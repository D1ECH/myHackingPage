## Qué está haciendo realmente ese XSLT
El elemento clave es este:
```xml
<ptswarm:document href="/var/www/conversor.htb/scripts/test2.py" method="text">
```
Eso **NO es XSLT estándar**.
Eso es una **extensión**.
En libxslt existen extensiones EXSLT que permiten crear archivos durante la transformación.  
El elemento real se llama normalmente:
```
exsl:document
```
Pero aquí lo han declarado así:
```xml
xmlns:ptswarm="http://exslt.org/common"
extension-element-prefixes="ptswarm"
```
O sea:
- Está usando el namespace de EXSLT.
- Pero lo ha llamado `ptswarm`.
Eso es solo un alias. El namespace es lo importante.
## Por qué funciona en TU código
Mira tu backend:
```python
xslt_tree = etree.parse(xslt_path)
transform = etree.XSLT(xslt_tree)
result_tree = transform(xml_tree)
```
No hay:
```python
etree.XSLTAccessControl(...)
```
En lxml, si no defines `access_control`, el comportamiento por defecto es PERMISIVO.
Eso significa:
- Puede leer archivos 
- Puede escribir archivos
- Puede usar extensiones EXSLT
Entonces cuando el transformador procesa:
```xml
<ptswarm:document href="/var/www/conversor.htb/scripts/test2.py">
```
libxslt crea realmente ese archivo en el sistema.
No es magia.  
No es RCE directa.  
Es el propio motor XSLT escribiendo el archivo.
El proceso que ejecuta Flask tiene permisos sobre `/var/www/conversor.htb/`.
Así que lo crea.
## Cómo pensó esto quien lo resolvió
El razonamiento fue algo así:
### Paso 1 — Veo que usan lxml
→ Sé que debajo está libxslt.
### Paso 2 — Veo que no usan XSLTAccessControl
→ Eso significa que EXSLT puede estar activo.
### Paso 3 — Busco qué extensiones soporta libxslt
libxslt soporta:
- exsl:document → escribir archivos 

Eso es conocido y está documentado.
### Paso 4 — Si puedo escribir archivos…
Entonces me pregunto:
¿Dónde puedo escribir?
Viendo el código:
```
/var/www/conversor.htb/
```
Y probablemente exista:
```
/var/www/conversor.htb/scripts/
```
Y si esa carpeta está dentro del entorno ejecutable…
Ya tienes ejecución indirecta.
